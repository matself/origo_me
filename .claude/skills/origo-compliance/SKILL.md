# Contributing to Origo, in compliance

This distils `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, `DEVELOPING.md`, `LICENSE.txt`,
`PLUGINS.md`, `README.md` and `SECURITY.md` into the rules that actually change what you write.
Where a rule is enforced automatically, that is called out — those are the ones that block a
merge, so they are worth getting right the first time.

The upstream project is `origo-map/origo`. **This repository is a fork** (`matself/origo_me`),
which changes a few things at the end — see [Fork-specific rules](#fork-specific-rules).

## The hard gate: lint

`.github/workflows/lint.yml` runs `npm run lint` on **every push and every pull request**. There
is no warning tier — any ESLint error fails the build, so run it locally before you commit:

```bash
npm run lint
```

`npm run lint-fix` auto-fixes what it can. `npm run lint-run` starts the dev server with linting
in the pipeline; `npm run lint-build` lints and builds.

JavaScript follows [Airbnb's style guide](https://github.com/airbnb/javascript) for ES6, via
`.eslintrc.json` (`airbnb-base` with a few relaxations: `max-len` off, import cycles allowed,
no trailing commas).

When a rule genuinely cannot be satisfied, disable it for the single line and say why. The
codebase does this about seventy times, always in this shape:

```js
// Circular by design: the tool registry needs the handler that registers it.
// eslint-disable-next-line no-use-before-define
```

A bare disable comment with no reasoning is the thing reviewers push back on — the next person
needs to know whether the exception is still load-bearing.

CodeQL also runs on pushes, PRs and weekly, so avoid patterns that will trip static analysis
(unsanitised HTML injection in particular, given how much of the UI is built from strings).

## Language and dependencies

Origo is ES6, HTML5 and CSS3, bundled by webpack. Two constraints shape what you may add:

**Avoid framework dependencies.** The stated ambition is small libraries used as building
blocks, not growing Origo into a large framework. Before reaching for a package, check whether
the core already has something: `ol` covers most geometry and rendering, `proj4` covers
projections, and `src/ui/` has a component base plus a widget kit. Plugins in particular should
exhaust the core's existing dependencies first.

**Check the licence.** Origo is BSD 2-Clause. Any third-party library must carry a compatible
licence — that rules out GPL and other copyleft terms. This is a legal constraint on the
project, not a preference, so verify before adding rather than after.

Browser support is Edge, Firefox, Chrome and Safari. Progressive enhancement is explicitly
encouraged: it is fine to use a newer API that only modern browsers support, **provided the
functionality it powers is not critical** — the map still has to work without it.

OpenLayers is the map component, at the version in `package.json`. Server-side concerns live in
a separate repository (`origo-map/origo-server`) and are out of scope here.

## CSS and SCSS

* **Edit `.scss` only.** `css/style.css` is generated by Dart Sass and is gitignored — changes
  made there are lost on the next build. Partials live in `scss/`, roughly one per control.
* **Prefix every class and id with `o-`** (`o-map`, `o-share-link`, `o-toolbar-navigation`).
  Origo is embedded into host pages that have their own stylesheets; the prefix is what stops
  the two from colliding.
* Follow the [Airbnb CSS/SASS guidelines](https://github.com/airbnb/css).
* Verify additions do not conflict with existing rules — the stylesheet is one flat bundle with
  no scoping.
* **Icons must be SVG**, chosen from Material Icons first, Font Awesome second. Both ship as
  sprites (`css/svg/`). A new library has to be added as a sprite too, not linked per-icon.
* **Do not add media queries for layout breakpoints.** Origo sizes itself against the *map
  element*, not the browser window, so it implements element-query-like breakpoints defined in
  the configuration file (`breakPoints` / `breakPointsPrefix`, defaulting to the `o-media`
  prefix). A media query would respond to the wrong box entirely on an embedded map.

## Commits and pull requests

**Open an issue first.** For anything beyond a trivial fix, describe what you intend to change
and wait for a core developer to confirm before opening the PR. This is the project's stated
process and it saves rejected work.

**PR titles take a prefix**, one of:

| Prefix | For |
| --- | --- |
| `dep:` | Dependency updates |
| `docs:` | Editing `.md` files in this repo |
| `feature:` | New functionality |
| `fix:` | Bug fixes, or rewrites that add no new functionality |

**One PR, one thing.** A single issue or a single item of functionality. Commits inside it
should be logical and incremental — rebase locally to clean up the history before opening, and
make sure it merges without conflicts.

**Documentation is part of the contribution.** A functional change needs a matching PR against
the documentation repository, cross-linked to the code PR. Keep documentation short and simple,
and include a code example where one helps.

**Commit messages follow the OpenLayers format:**

```
Header line: explain the commit in one line, under 50 characters

Body giving background — why the change was needed, what it does that
is not obvious from the diff. Wrap at about 74 characters so git log
stays readable when indented.

Further paragraphs after blank lines.
```

Write the body for someone reading `git log` in two years without the issue open.

## Core or plugin?

`PLUGINS.md` draws the line clearly: build a **plugin** when the feature has external
dependencies, or when it is specific enough that the average Origo user would not want it.
Build in **core** only when it is broadly useful and dependency-light.

For plugins:

* Start from [barebone-plugin](https://github.com/origo-map/barebone-plugin) for structure.
* Use core's existing dependencies before loading new ones.
* Keep the plugin standalone — small core adjustments are sometimes necessary but should be
  minimised, because every one of them couples your release cycle to Origo's.
* If the plugin has a UI with text, use the core localization control so it works in every
  language the host map offers.

Plugins are consumed through `options.controls` and resolved by name like built-ins; `Origo.ol`,
`Origo.ui` and `Origo.Style` are re-exported so a plugin shares the host's OpenLayers instance
rather than bundling its own.

## Security and licence

* **Supported versions**: 2.x receives fixes; 1.x does not.
* **Reporting a vulnerability**: the project's stated channel is a GitHub issue, the same as any
  bug. Be aware this is a *public* channel — for a serious unpatched vulnerability, consider
  contacting maintainers privately first (the Discord server or the Code of Conduct contact) and
  say so rather than posting exploitable detail in the open.
* Dependencies are audited for security updates during upgrades; Dependabot PRs land regularly
  and should be merged promptly rather than accumulating.
* The BSD 2-Clause licence requires the copyright notice and disclaimer to be retained in both
  source and binary redistributions. If you ship a bundle, the notice travels with it.

## AI-assisted contributions

**Origo has no AI policy.** As of 2026-08-28 there is nothing about AI, LLMs, generated code or
assisted contributions in the repository's policy files (which are byte-identical to upstream
`origo-map/origo`), in the published documentation, in the documentation repository, or in an
organisation-wide `.github` repository — that last one does not exist. So there is no disclosure
requirement to satisfy and no prohibition to work around.

What that absence means in practice: **the contributor owns the contribution regardless of how
it was produced.** No rule is relaxed because a tool wrote the diff, and three of the existing
rules bite harder on generated code than on hand-written code.

**Provenance is a licence question, not a style question.** `DEVELOPING.md` requires every
third-party library to carry a licence compatible with BSD-2, because the project has to be able
to relicense what it ships. Submitting code means asserting it is yours to contribute under
those terms. Generated code that reproduces a substantial chunk of some other project sits in
exactly the same risk category as an incompatible dependency — with the difference that nobody
can see it in the diff. Treat anything that looks like it came from a recognisable upstream as
something to verify, not to assume.

**The lint gate does not care who wrote it.** Airbnb rules that generated JavaScript commonly
trips: `comma-dangle: never`, `no-use-before-define`, `no-param-reassign`, `prefer-const`. Run
`npm run lint` before proposing anything — CI runs it on every push, so an unlinted PR fails
before a human reads it. Never report that checks pass without having run them.

**Origo's local conventions are the ones a model will not know**, because they are unlike
general web practice and are not in most training data. Check generated code specifically for:

* the `o-` prefix on every CSS class and id;
* styling changed in `.scss`, never in the generated `css/style.css`;
* breakpoints via Origo's configuration-driven element queries rather than media queries;
* templating with ES6 template literals — **not** Handlebars, which `DEVELOPING.md` still
  wrongly claims is used (see [Known documentation drift](#known-documentation-drift)). A model
  reading the project's own documentation will suggest the wrong thing here.

**Keep the diff reviewable.** `CONTRIBUTING.md` asks for one issue per PR, logical incremental
commits, and an issue opened before the work starts. Generated changes tend to sprawl across
files and arrive as one large commit, which is precisely what that process exists to prevent.
Split the work the way you would have if you had written it by hand, and be able to explain
every line in review — a maintainer's time is the scarce resource, and unreviewable volume
spends it fastest.

**Commit trailers are a fork-local practice.** This fork records assistance with a
`Co-Authored-By:` trailer on commits that had it. Upstream neither requires nor forbids this;
decide deliberately whether such trailers belong on a PR aimed at `origo-map/origo`.

## Conduct

The project uses the Contributor Covenant v1.4 (`CODE_OF_CONDUCT.md`), covering issues, PRs,
reviews, the Discord server and any space where someone represents the project. The practical
form it takes in review: critique the code rather than the person, and assume the contributor
had a reason. The enforcement contact is listed in `CODE_OF_CONDUCT.md`.

## Fork-specific rules

This repository is a fork, which adds obligations the upstream docs do not mention:

* **`build/` is committed here.** `build/js/origo.js` and `origo.min.js` are tracked, so any
  change under `src/` must be followed by `npm run build` and the regenerated bundles committed
  alongside it. A source change that ships without a rebuild silently does nothing in
  deployment. Dependency-only changes do not need a rebuild.
* **Upstream contributions target `origo-map/origo`,** not this fork. Keep changes intended for
  upstream free of fork-local tooling so they can be cherry-picked cleanly.
* **Prefer not to modify or delete upstream code without cause.** Every local edit to a core
  file becomes a merge conflict on the next upstream sync. Additive tooling in `tools/`,
  `admin-editor/` or `.claude/` costs nothing at merge time; edits inside `src/` cost forever.
* Merge upstream regularly — the fork is deployment infrastructure, so falling behind on
  security bumps is the main hygiene risk. See `CODEBASE-ATLAS.md` for the current state.
* **GitHub Actions is deliberately switched off here, so nothing verifies a push.** GitHub
  disables Actions on forks until the owner turns them on, and that has been left that way on
  purpose — the demo-map workflow is written for upstream and would only fail here. Do not read
  the three workflow files as evidence that CI runs: the API reports all three as `active`
  because that is the workflow files' own state, not the repository's, and this fork has zero
  workflow runs in its entire history. **Run `npm run lint` locally before pushing** — it is the
  same command, config and coverage as `lint.yml`, just on your Node version rather than Node
  20. The lint gate returns when a branch reaches `origo-map/origo`.

## Known documentation drift

These points in the project docs no longer match the code. Follow the code; consider a `docs:`
PR upstream to fix the file.

* **`DEVELOPING.md` says Origo uses Handlebars.js for templating.** It does not — Handlebars is
  not in `package.json` and is imported nowhere. Templates are plain ES6 template literals; see
  `src/templates/viewertemplate.js` and the helpers in `src/utils/templatehelpers.js`. Write new
  templates the same way.
* **`CONTRIBUTING.md` names the wrong documentation repository.** It sends documentation PRs to
  `origo-map/api-documentation`; the live repository is
  [`origo-map/origo-documentation`](https://github.com/origo-map/origo-documentation)
  ("Api documentation for Origo"), which is what `README.md` and `PLUGINS.md` link to and what
  publishes the site at
  <https://origo-map.github.io/origo-documentation/latest/#origo-api>. Verified 2026-08-28.
  Open documentation PRs against `origo-documentation`.

## Quick pre-flight

Before proposing a change, walk the list:

1. `npm run lint` clean — the CI gate upstream, and in this fork nobody runs it but you.
2. Styling changed only in `.scss`, every new selector prefixed `o-`, no layout media queries.
3. New dependency? Licence compatible with BSD-2, and not a framework.
4. Touched `src/` in this fork? Rebuild bundles and commit them.
5. Commit message: ≤50-character header, wrapped body explaining why.
6. PR title prefixed `dep:` / `docs:` / `feature:` / `fix:`, scoped to one thing.
7. Functional change? Documentation PR opened and cross-linked.
